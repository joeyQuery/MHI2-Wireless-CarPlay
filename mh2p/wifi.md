# MH2p Wi-Fi Access Point for Wireless CarPlay

How the MH2p (`MH2p_ER_AUG33_P2873`, `MMX2P` 2201.8.0) builds the Wi-Fi access point that its production
wireless CarPlay uses, and what that means for an MHI2 / MHI2Q `uap0`.

> **Scope rule.** Everything in the "MH2p facts" sections is static evidence from the MH2p firmware
> (see [firmware.md](firmware.md)). It is **cross-platform evidence**, not proof of MHI2 behaviour.
> Statements about MHI2 / MHI2Q are marked as inference unless they cite an MHI2Q file.
> Evidence IDs P-200..P-2xx are listed at the end.

Paths below are relative to `<MH2p>/` unless stated (see [README](README.md#paths)). Addresses are file/virtual
addresses from `ntoarmv7-objdump` (Ghidra adds +0x10000).

**Extraction note.** `/etc/boot/drivers.sh`, `services.sh`, `/etc/pf.conf`, `/etc/pf.mlan0.conf` and
`/etc/dhcp/*` are in `stage2_ifs4/` (they were missing from the first extraction and have since been
extracted in place). Boot order, the full `pf.conf` and the rest of the boot scripts are covered in
[configuration-and-boot.md](configuration-and-boot.md) (P-100..P-123); this document only quotes the
lines that matter for the Wi-Fi AP.

## 1. Summary

| Question | MH2p answer |
| --- | --- |
| Chip / driver | Broadcom BCM4359, `io-pkt` driver `devnp-qwdi-2.5_bcm4359-wapi.so`, firmware `fw_bcmdhd_4359.bin` + nvram + CLM blob |
| Interfaces | `bcm0` = **5 GHz AP** 10.174.189.1/24, `bcm1` = 2.4 GHz AP 10.173.189.1/24, `bcm2` = station (client), `bcm_p2pdev0` = P2P device. All from one chip, concurrently |
| Which AP CarPlay uses | `bcm0`, the **internal 5 GHz AP** (`smartphone_integrator.json` `wireless.mDNSDiscovery.wifiInterfaceName = "bcm0"`, `dio_manager.json` `wifi.ifname = "bcm0"`, `ipaddr = "10.174.189.1"`) |
| Separate CarPlay AP? | Yes in practice: an "internal AP" (`bcm0`, used by CarPlay and Android Auto) and a "customer AP" (`bcm1`, the user hotspot). `gal.json` names them `interfaceNameInternalAP` / `interfaceNameCustomerAP` |
| AP software | `hostapd-2.5-wapi`, one instance per interface, config generated by `connectionmanager` from `/eso/telephone/ap0.config` (5 GHz) / `ap1.config` (2.4 GHz) |
| 5 GHz config | `hw_mode=a`, `ieee80211n=1` `[HT40+]`, `ieee80211ac=1`, `vht_oper_chwidth=0` (80 MHz off), `wme_enabled=1`, `max_num_sta=8`, WPA2-PSK CCMP |
| Channel | Per country from `mcc_countrycode.xml`: only **36** or **149** (both non-DFS); 5 GHz disabled entirely in 62 of 172 countries |
| Apple vendor IE | Yes. `connectionmanager` `WLAN::setAppleIE` runs `wl -i bcmN add_ie 7 <len> 00:a0:40 <hex>`: OUI type 0, TLVs flags / name `MIB2P` / model `A8` / manufacturer `Audi AG` / Bluetooth MAC |
| Credentials to iAP2 | `connectionmanager` (ASI `asi.connectivity.networking.WlanService`, `updateinternalApDetails`) -> `smartphone_integrator` (`WiFiAPInfoProvider`) -> `iap2connectionmanager` (ASI `asi.media.iap2connection.IAP2Connection`, `iap2AccessoryWiFiConfigurationInformation`) -> `libesoiap2.so` `CIAP2ControlSessionModuleWifiShare` -> iAP2 `0x5703` |
| DHCP | `dnsmasq -i bcm0 -i bcm1`, range 10.174.189.128-.247 on `bcm0`, lease 3 days, router option suppressed while there is no uplink |
| mDNS | `mdnsd` started **at boot**, all interfaces, with `MDNS_DIRECTLINK_IFACE=carplay0` set on its command line |
| Firewall | `pf.conf` opens the CarPlay port set (incl. TCP 7000 and 6030) and mDNS (v4 and v6) on **both** APs; per-AP priority queues |
| Without 5 GHz | `smartphone_integrator` refuses: "5GHz access point is not available to activate Wireless CarPlay for deviceID=%i." |

## 2. Hardware and driver (MH2p facts)

### 2.1 Driver start: `start_wifi_driver` (`/etc/boot/drivers.sh`, lines 94-165)

Called from `startup.normal.sh:28`, `startup.production.sh:26`, `startup.test.sh:19`, and again by
`app/eso/bin/reset_wlan.sh` (which first destroys `bcm_p2pdev0`, `bcm2`, `bcm1`, `bcm0`).

Key lines, in order:

```sh
sysctl -w kern.sbmax=2949120
sysctl -w net.inet.ip.forwarding=1
sysctl -w net.inet.tcp.recvspace=128480 ; sysctl -w net.inet.tcp.sendspace=128480
FW="/var/FwImage/fw_bcmdhd_4359.bin"
NVRAM="/var/FwImage/nvram_4359_c_samples.txt"      # nvram_4359.txt if REVISION < 200
CLM=/var/FwImage/4359b1.clm_blob
mount -Tio-pkt -o qwdi_clm_path=${CLM},fw=${FW},nvram=${NVRAM} /lib/dll/devnp-qwdi-2.5_bcm4359-wapi.so
### Broadcom 5.0 GHz hotspot ##
ifconfig bcm0 10.174.189.1 netmask 255.255.255.0 ; ifconfig bcm0 up
wl ap 1 ; wl frameburst 1 ; wl cur_etheraddr > /tmp/brcm_wifi ; >/tmp/uap0
### Broadcom 2.4 GHz hotspot ###
ifconfig bcm1 10.173.189.1 netmask 255.255.255.0 ; ifconfig bcm1 up ; >/tmp/uap1
ifconfig bcm2 up
>/tmp/mvloaded
```

- Firmware files (all in `app.img`, `app_list.txt`): `var/FwImage/fw_bcmdhd_4359.bin` (606,852 B),
  `fw_bcmdhd_mfgtest.bin` (manufacturing, used when `/var/mvmfgmode` exists), `nvram_4359.txt`,
  `nvram_4359_c_samples.txt`, `PAG/nvram_4359_c_samples.txt`, `4359b1.clm_blob` (regulatory CLM).
  Bluetooth is the same combo: `BCM4349B1.hcd` loaded by `hcdloader` in `start_bluetooth_driver`, which
  waits for `/tmp/mvloaded`.
- The marker files keep their Marvell names: `/tmp/uap0` = "5 GHz AP up", `/tmp/uap1` = "2.4 GHz AP up",
  `/tmp/mvloaded` = "Wi-Fi driver loaded". `/tmp/brcm_wifi` holds the chip MAC and tells scripts that the
  Broadcom path is active.
- **Interfaces**: `bcm0` (AP 5 GHz), `bcm1` (AP 2.4 GHz), `bcm2` (station: `dhcp-check`/`dhcp-up` treat
  `bcm2` as the DHCP-client uplink, and `pf.mlan0.conf` sets `ext_if = "bcm2"`), `bcm_p2pdev0`
  (`reset_wlan.sh`). No `wlan0`/`wl0.1`/`uap0` interface exists on the Broadcom path.
- **Concurrency**: two APs plus a station on one BCM4359 at the same time. `connectionmanager` also drives
  `wl rsdb_mode %d` ("5G_old:%d 5G_new:%d rsdb_cur:(%d) rsdb_new:%d", string at 0xfee88), i.e. the
  BCM4359's real-simultaneous-dual-band mode, when the 5 GHz AP is switched.
- `usr/sbin/pci-starter.sh` (`determine_wifi_chip`) probes PCI vendor `0x14e4` (Broadcom) or `0x11ab`
  (Marvell): the platform was designed for either chip.

### 2.2 Marvell fallback left in MH2p

MH2p still carries a Marvell AP path for early ("B") samples:

- `app/eso/telephone/start-ap.sh`: `uaputl -i uap0` 2.4 GHz, `sys_cfg_channel 6`, `sys_cfg_11n 1 0x17C 3 0 0xffff`,
  `coex_config /eso/telephone/coex.cfg`, `aggrpriotbl ...` ("disable packet aggregation for WMM video streams").
- `start-ap5g.sh`: `uaputl -i uap1 sys_cfg_channel 36 2`, `sys_cfg_11n 1 0x117E ...`, `vhtcfg 2 3 1 ...`.
- `connectionmanager` writes `/tmp/ap1_config.cfg` (`ChanList=1,6,11`, 2.4 GHz) and `/tmp/ap2_config.cfg`
  (`ChanList=36`, `Channel=36,2`, `Protocol=32`, `PwkCipherWPA2=8`) for those scripts (strings 0xff150-0xff2f0,
  0x100138-0x100368).
- `switchpf.sh` ("remove when B-Samples deprecated") rewrites pf rules `bcm1 -> uap0`, `bcm0 -> uap1`.
- `restart_dnsmasq.sh` starts `dnsmasq -i uap0 -i uap1` when `/tmp/brcm_wifi` is absent.

`uaputl` itself is **not** shipped in this release (`app_list.txt` has no `uaputl`), so this path is dead
code here. It matters as design evidence (section 7).

## 3. AP configuration for CarPlay (MH2p facts)

### 3.1 hostapd instances (`connectionmanager`, source `HostapdInstance.cxx`)

- Binary `/armle/usr/sbin/hostapd-2.5-wapi` (string 0x107400), one instance per AP: pid files
  `/var/run/hostapd-bcm0.pid` / `-bcm1.pid` (0x1004fc / 0x1004e0), control dir `/var/run/hostapd`,
  instance names `ap5g` / `ap2g`, trace channels `CON_CONMAN_WLAN_AP5G` / `_AP2G`.
- Template `/eso/telephone/ap<N>.config` (strings `/eso/telephone/ap` + `%u` + `.config`, 0x107008),
  output `/tmp/ap.config.bcm<N>` (0x106f64), function at 0xa91f2 (`template_file=%s`).
- Placeholders replaced (0x107040-0x1071f8): `$$INTERFACE$$`, `$$DRIVER$$` (config
  `connectivity.json` `connectionmanager.wifidriver = "qwdi"`, default `broadcom`), `$$SSID$$`,
  `$$CHANNEL$$`, `$$BROADCAST_SSID$$`, `$$PASSPHRASE$$`, `$$CTRL_INTERFACE$$`, `$$WPSSTATE$$`
  (`wps_state=2` or `#wps_state=2`), `$$UUIDPART$$`, and `$$ENCRYPTION$$`, which becomes one of:

  ```text
  wpa=2  wpa_passphrase=$$PASSPHRASE$$  wpa_key_mgmt=WPA-PSK  wpa_pairwise=CCMP  rsn_pairwise=CCMP
         wpa_group_rekey=0  wpa_gmk_rekey=0  wpa_ptk_rekey=0
  wpa=4  wpa_key_mgmt=WAPI-PSK  wpa_pairwise=SMS4 ...              (China WAPI variant)
  ```

- `hostapd_cli` commands used: `VENDOR_IE ADD %d ` / `VENDOR_IE DEL %d` (0x106cd4, used at 0xa6304),
  WPS PBC/Cancel, deauthenticate. The `VENDOR_IE` command is not in stock hostapd 2.5, so this hostapd is
  a vendor build [Inference].

### 3.2 The 5 GHz template `/eso/telephone/ap0.config` (key lines)

```text
hw_mode=a            channel=$$CHANNEL$$   beacon_int=100   dtim_period=1   max_num_sta=8
supported_rates=60 90 120 180 240 360 480 540      basic_rates=60 120 240
auth_algs=1          ignore_broadcast_ssid=$$BROADCAST_SSID$$
wme_enabled=1 (per-AC parameters; VI txop 94, VO txop 47)   uapsd_advertisement_enabled=1
ieee80211n=1         ht_capab=[GF][SHORT-GI-20][SHORT-GI-40][RX-STBC1][HT40+]
ieee80211ac=1        vht_capab=[SHORT-GI-80]      vht_oper_chwidth=0     # "Set to 0 to disable 80MHz"
eap_server=1  config_methods=virtual_push_button  device_name=MIB2P Hotspot  manufacturer=e.Solutions
```

`ap1.config` (2.4 GHz, `bcm1`) is the same with `hw_mode=g`, `ht_capab=[GF][SHORT-GI-20][RX-STBC1]`, no 11ac.

Absent from both templates: `country_code`, `ieee80211d`, `ieee80211h`, `vendor_elements`,
`ap_isolate`. Country and the Apple IE are applied through Broadcom `wl` instead (below).

### 3.3 Band and channel selection

- `WLAN.Config_CLU28_MMX2P_AU_ER_G33_004PROD/0/connectivity/mcc_countrycode.xml` (from
  `<MH2p SWDL>/Data/`, installed to `/mnt/misc1/connectivity/mcc_countrycode.xml`, the path
  `connectionmanager` reads, string 0xfebc0): `records version="v2_2018_10_23_Clu26"`, 172 records with
  `alpha2`, `alpha3`, `mcc`, `active5Ghz`, `channel5Ghz`.
  - Channels used: only **36** or **149**. Neither is a DFS channel. Counts: `true/149` 98, `true/36` 12,
    `false/149` 32, `false/36` 30.
  - Examples: `DE mcc=262 active5Ghz="true" channel5Ghz="149"`; `US ... "true" "149"`;
    `CN ... "true" "36"`; `RU ... "true" "36"`; `JP ... "false"`.
- The country comes from the mobile network MCC, the navigation or the HMI (log "Wlan-5G-Reconfig: new
  source:%d mcc:%s ..." 0xfe940, `hmiSetCountryTimeout`, "Startup timeout, seting hmi country"). It is
  pushed to the chip with `wl country` (0x7aff2). A running AP moves channel with `wl -i bcm0 csa b 1 %d`
  (0x79c96, "switching to %d on %s").
- If `active5Ghz` is false the 5 GHz AP is disabled ("5GHz allowed but no channels found or disabled ->
  disabling", 0xfd588).
- HT40+ on 36 or 149 gives a 40 MHz channel (36+40, 149+153). 80 MHz is switched off in the template.

### 3.4 SSID and passphrase

- Default SSID prefix per brand (0xfd8b8-0xfd920): `Audi_MMI_`, `VW_WLAN_`, `Skoda_WLAN_`, `SEAT_WLAN_`,
  `Bentley_WLAN_`, `Porsche_WLAN_`, `LB_LIS_`. The 5 GHz SSID gets the suffix ` 5GHz` (0xfdc74). SSID
  generation waits for the VIN ("no VIN or user SSID, waiting 10s", 0xffdb4; "Startup timeout, generating
  a SSID", used at 0x6d6d6).
- Passphrase: `generateRandomPassword` (0x73e12) uses the alphabet `abcdefghijklmnopqrstuvwxyz` (0xfdd30);
  a profile with an empty password gets a generated default (0x84b92). Length check "Passphrase must be
  8..63 characters".
- A sample pair is hard-coded in `smartphone_integrator` next to its fake-5 GHz test job
  (`CControllerInternalJob_FakeWifi5GHzOnOff`): `Audi_MMI_**** 5GHz` / `****-****-****` (values masked here; strings 0xecf98,
  0xecfac). That shows the production format: `Audi_MMI_<4 digits> 5GHz`, passphrase `xxxx-xxxx-xxxx`
  [Inference from the sample and the alphabet].
- Stored as WLAN profiles by `connectionmanager` ("Profile adapted", "Overwriting default SSID '%s' with
  '%s'"); the exact persistence key was not traced.
- Visibility is a runtime value (`$$BROADCAST_SSID$$`, log "visible=%s"); whether the internal AP is hidden
  was not determined.

### 3.5 Vendor IEs added with `wl`

**Apple IE** (`networking_4WLAN` function at 0x7b370, log tag `setAppleIE`, called for `bcm0` and `bcm1`
from `onWifiIfcCarrier` (0x7c456/0x7c470) and from `updateLocalBluetoothAddress` (0x7c770, `bcm0`)):

```text
/mnt/app/armle/usr/sbin/wl -i <ifc> add_ie 7 <len> 00:a0:40 <hex payload>     (0x7b742-0x7b806)
/mnt/app/armle/usr/sbin/wl -i <ifc> del_ie 7 <len> 00:a0:40 <old payload>     (0x7b942-0x7b970)
```

Payload, reconstructed from the disassembly (TLV helper at 0x3f22c, called with the type in `r1`):

| Bytes | Meaning | Source |
| --- | --- | --- |
| `00` | OUI type 0 | 1-byte literal at 0xfc01c, 0x7b4da |
| `00 02 00 FF` | TLV 0 = flags (2 bytes) | 0x7b510-0x7b542 |
| `01 05 "MIB2P"` | TLV 1 = name | literal 0xfc020, `movs r1,#1` 0x7b592 |
| `03 02 "A8"` | TLV 3 = model | literal 0x101760, `movs r1,#3` 0x7b5dc |
| `02 07 "Audi AG"` | TLV 2 = manufacturer | literal 0x101a24, `movs r1,#2` 0x7b626 |
| `06 06 <BT MAC>` | TLV 6 = local Bluetooth address, only when known | `this+0x308` (u64), length checked `== 6` at 0x7b8ec |

- Flags byte `FF`: bit 0x01 set when the interface is `bcm0` (5 GHz; `strcmp` with "bcm0" at 0x7b49c);
  bit 0x20 set together with it only when a byte at `this+0x310` is non-zero, otherwise the whole byte is 0;
  bit 0x10 from a second state check (0x7b506). The meaning of `this+0x310` (probably "wireless CarPlay
  enabled") was not traced.
- `<len>` = payload bytes + 3 (`lsrs r2,r3,#1; adds r2,#3` at 0x7b7ec: hex length / 2 + OUI).
- `pktflag 7` = beacon + probe response + association response under Broadcom's `wl` vendor-IE flag bits
  [Inference: Broadcom convention, not in this firmware].
- No IE is set until the interface is up and the BT address is known ("not setting apple-ie: ifc not up
  yet", "... btaddress not yet available"); an unchanged payload is not re-sent ("old-ie: unchanged
  payload").
- Cross-check: LIVI (`LIVI/native/livi-helperd/crates/livi-runtime/src/wifi_ap.rs:69`) sends
  `dd0800a04000000200<0x20|band>` as hostapd `vendor_elements` and `assocresp_elements`, band bit 0x01 for
  channel >= 36, 0x02 otherwise. Same OUI, OUI type and flags TLV; MH2p adds name/model/manufacturer/BT MAC.

**Interworking IE** (`setInterworkingIE`, 0x79800): `wl -i bcm0 ie 107 3 <hex>` with payload built from
`"0"|"1"` + `"00a01"|"20a01"`, i.e. access-network-options byte then venue group 0x0A / type 0x01
(802.11u "Vehicular / Automobile") [decoding is Inference]. Also run for `bcm1`.

**Link tuning on carrier up** (`onWifiIfcCarrier`, 0x7bb60-0x7bd90): `wl -i <ifc> srl 15`, `lrl 15`
(retry limits), `ampdu_rts 0`, `scb_activity_time 1`.

- `dio_manager` is **not** in this path: it has `CIAP2WiFiInformationSharing` with

- `connectionmanager` also feeds the same fields (ssid, pw, bssid, country, channel, visibility,

## 5. IP layer (MH2p facts)

### 5.1 DHCP / DNS: `/etc/dnsmasq.conf`, started by `start_dnsmasq` (`services.sh:100-109`)

```text
interface=lo0
dhcp-range=10.173.189.128,10.173.189.247,255.255.255.0,3d      # bcm1 (2.4 GHz)
dhcp-range=10.174.189.128,10.174.189.247,255.255.255.0,3d      # bcm0 (5 GHz, CarPlay)
domain=mib2p,10.174.189.0/24        local=/mib2p/      dhcp-lease-max=200
dhcp-optsfile=/ramdisks/sys/connect/dhcp-opts     conf-file=/tmp/dnsmasq.sdis.conf
```

Command line: `/eso/bin/apps/dnsmasq -i bcm0 -i bcm1` after both `/tmp/uap0` and `/tmp/uap1` exist.
`/eso/telephone/modWLANserver.sh` writes `3\n` (empty option 3 = no default router) when there is no
internet uplink and removes it when there is, then `SIGHUP`s dnsmasq; `connectionmanager` writes the
opts file (0xfefc0). So a CarPlay phone gets an address and DNS from the car but **no default gateway**
unless the car has an uplink, which keeps the phone's cellular data as its route. `/tmp/dnsmasq.sdis.conf`
holds static `dhcp-host=` entries for rear-seat devices only.

### 5.2 IPv6 and mDNS

- `mdnsd` starts at boot (`startup.normal.sh:41` -> `services.sh:364-368`):
  `MDNS_DIRECTLINK_IFACE=carplay0 mDNSPlatformDefaultProbeCountForTypeUnique=0 /mnt/app/armle/usr/sbin/mdnsd -U mdnsd &`.
  No interface restriction: it serves every multicast interface, `bcm0` included. `carplay0` is only the
  direct-link (USB NCM) interface.
- `smartphone_integrator` browses `_carplay-ctrl._tcp` on `bcm0` (`wireless.mDNSDiscovery`), and reports
  "mDNS background daemon not running" if `mdnsd` is absent.
- pf (below) passes `ipv6-icmp` and UDP 5353 to `FF02::FB` on both APs, and the CarPlay TCP/UDP rules are
  address-family neutral, so IPv6 link-local works on the APs. Whether AirPlay itself binds IPv4
  (10.174.189.1) or IPv6 link-local on `bcm0` was not traced.

### 5.3 Firewall: `/etc/pf.conf` (loaded by `start_packet_filter`, `services.sh:58-91`)

The full rule set is in [configuration-and-boot.md](configuration-and-boot.md). The parts that define
the CarPlay AP: macros `wlan_if = "bcm1"` (2.4 GHz), `wla2_if = "bcm0"` (5 GHz); rules for `bcm0`
(lines 138-212; `bcm1` is identical):

```text
altq on $wla2_if priq bandwidth 300Mb qlimit 400 queue { ... video_out, audio_out, control_out ... }
block in quick on $wla2_if from any to {($ext_if:network), ($dbg_if:network), ($int_if:network)}
pass  in quick on $wla2_if inet proto udp from any port bootpc to any port bootp ...
block in quick on $wla2_if inet from !($wla2_if:network) to any
pass  in quick on $wla2_if inet6 proto ipv6-icmp from any to {($wla2_if), FF00::/8} ...
pass  in quick on $wla2_if inet  proto udp from any to 224.0.0.251 port 5353
pass  in quick on $wla2_if inet6 proto udp from any to FF02::FB port 5353
pass  in quick on $wla2_if proto tcp from any to ($wla2_if) port 7300 ...              # Android Auto
# allow CarPlay wireless (and indirectly iperf)
pass  in quick on $wla2_if proto tcp from any to ($wla2_if) port 6030 keep state (max 99, ... max-src-conn 98)
pass  in quick on $wla2_if proto tcp from any to ($wla2_if) port { 5000:5001, 5010, 6000:6001, 6100, 6200, 7000:7001, 7100 } ...
pass  in quick on $wla2_if proto udp from any to ($wla2_if) port { 5001, 5020, 5353, 6000:6003, 6010:6011, 6020:6021, 7010:7011, 7070:7071 } ...
...
block in quick on $wla2_if from any to ($wla2_if)          # everything else to the car
block in quick on $wla2_if from any to ($wlan_if:network)  # no traffic between the two APs
```

The Wi-Fi port set equals the `carplay0` set (lines 256-257) with UDP 67:68 handled separately. The
per-AP ALTQ queues give video/audio/control priority. `pf.mlan0.conf` is the variant with `bcm2`
(station uplink) as `ext_if`.

## 8. Answers for the MHI2 repo

- **STATUS Q4 / TRACE-003 (who exports `MDNS_DIRECTLINK_IFACE`)**: on MH2p the boot script exports it
  inline on the `mdnsd` command line (`services.sh:367`). On MU1329 it is `dio_manager`'s per-session
  launch (separate MU1329 analysis). Cross-platform evidence that the variable is a launch-environment setting of
  `mdnsd`, not something `mdnsd` or AirPlay derive. Does not prove the MU0678 producer.
- **STATUS Q8 / roadmap 4 ("Can the AirPlay/mDNS path operate on `uap0` without modification?")**: MH2p's
  answer for its own stack: mDNS does **not** need the direct-link mechanism for Wi-Fi; `mdnsd` serves the
  AP as an ordinary multicast interface while `MDNS_DIRECTLINK_IFACE` stays `carplay0`. What MH2p *does*
  need on the AP is: `mdnsd` running when the phone joins, pf passes for 5353 and the AirPlay ports, and
  the DIO Wi-Fi ifname. For MHI2Q MU1329 the pf part is known to fail as shipped (no 5353/7000 on `uap0`),
  and `mdnsd` is per session. So "without modification" is **no** for MU1329's configuration [Inference
  from config]; the binaries themselves may need no change [not determined].
- **TRACE-005 (AirPlay network binding)**: MH2p `dio_manager` uses `carplay0` for USB; for a Wi-Fi
  connection (or `WIFI_FORCE`) it uses the interface that holds `WIFI_IPADDR` (`dio_manager.json`
  `wifi.ipaddr` 10.174.189.1, found via `getifaddrs`), logging "<DIO> wifi interface: %s (%s)", and
  falls back to `bcm0` if `/tmp/brcm_wifi` exists, else `uap0` (0x7f940-0x7fd44). The decompile in
  [airplay-dio.md](airplay-dio.md) shows `WIFI_IFNAME` (`wifi.ifname`) is **not** read there; an earlier
  reading of this range assumed it was (see P-217). This is where a production
  receiver gets its Wi-Fi interface name; the MU1329/MU0678 equivalent should be looked for next to the
  `"uap0"` string in their `dio_manager`.
- **Roadmap 4 / docs/wifi.md 2.4 ("CarPlay-specific DHCP/DNS requirements")**: MH2p's CarPlay AP uses a
  plain dnsmasq range, 3-day leases, no router option without uplink, DNS from the car. Nothing
  CarPlay-specific beyond that.
- **docs/wifi.md 2.6 (PF)**: section 5.3 gives the production port list for CarPlay over Wi-Fi.
- **docs/wifi.md 2.7 (coexistence)**: MH2p's Marvell path used `coex_config /eso/telephone/coex.cfg`
  with the same `APBTCoex=0`, `btTime=40 wlanTime=60` values as MU0678; the Broadcom path has no such file
  (coexistence is in the combo-chip firmware) [Inference].

## 9. What this means for MHI2 / MHI2Q wireless CarPlay

1. The Wi-Fi side of a production unit is ordinary: WPA2 AP, dnsmasq, mDNS, pf holes, plus one Apple
   vendor IE. None of it needs a new driver feature that `uaputl` lacks, **except possibly 5 GHz RF**.
2. 5 GHz is the open hardware question. MH2p treats it as mandatory. `uaputl` accepts 5 GHz settings;
   whether the MHI2/MHI2Q 88W8787 module's antenna path works on 5 GHz is unknown. A read-only check
   (`uaputl -i uap0 sys_cfg_channel_ext 36 1 ...` on a bench unit, or reading `sys_cfg_scan_channels`)
   is the cheapest next step [not run; nothing was run on a car].
3. The Apple IE can be reproduced with `sys_cfg_custom_ie` using the MH2p/LIVI layout.
4. The phone credentials path on MH2p is connectionmanager -> smartphone_integrator -> iAP2 control
   session. MHI2Q MU1329 has no wireless code in any of those (separate MU1329 analysis), so on MHI2Q the 0x5703
   answer would have to be produced by our own code reading `/tmp/uaputl.cfg` [Inference].
5. MHI2Q changes needed on the AP side (all runtime or config): open pf on `uap0` for 5353 and the port
   set above, run `mdnsd` covering `uap0`, add the Apple IE, and move the AP to 5 GHz if the hardware
   allows.

- Whether AirPlay on MH2p binds IPv4 10.174.189.1 or IPv6 link-local on `bcm0`.
- The 0x5703 security-type and channel encoding inside `libesoiap2.so` (only symbols read).
